# Diccionario de datos

Actualización 2026-10-25: añadido `image_upload_intents` mediante migración nueva
20261024_image_upload_intents, sin modificar la inicial. Campos: id PK,
product_id FK, actor_id FK, public_id único, expected_version nullable,
expected_public_id nullable, expires_at, consumed_at nullable y created_at con
default UTC. Índice de expiración/consumo. El intent pertenece al administrador
creador y a un producto; vence en 10 min y se consume una vez. CAS compara
public_id y versión. No almacena archivos ni secretos Cloudinary.

Modelo lógico consolidado con ADR 0001–0012 y cuestionario. El esquema físico
implementado se consulta en `prisma/schema.prisma` y sus migraciones; este
documento también conserva el diseño de referencia de los flujos pendientes.
PK: clave primaria; FK: referencia;
UQ: único; `?`: nullable. IDs internos BIGINT, dinero como enteros
en centavos, fechas UTC. No eliminar históricos físicamente.

Motor elegido: PostgreSQL (ADR 0001). Tipos aceptados para el diseño físico (ADR 0004):
`BIGINT GENERATED BY DEFAULT AS IDENTITY` para IDs y `TIMESTAMPTZ` para
instantes. Prisma 7 y migraciones aprobados en ADR 0002. IDs y dinero BIGINT en centavos se serializan como strings decimales en JSON; fechas ISO 8601 UTC. Estas decisiones están aceptadas; faltan longitudes finales, CHECK, índices y migraciones concretas, no elegir nuevamente tipos/ORM.

## 2. Catálogo y personalizaciones

Imágenes: proveedor Cloudinary Free aceptado en ADR 0010. image_url se conserva;
image_public_id e image_version conservan referencia de reemplazo/limpieza. Una imagen JPEG/PNG/WebP por producto, máximo 5 MiB; carga firmada, validación y reemplazo seguro. orders.ready_by_employee_id audita quién marca LISTO (PREPARACION/CAJERO/ADMINISTRADOR). Los modelos y migraciones de catálogo están implementados; Cloudinary real sigue pendiente y se usa proveedor simulado en pruebas.

Estados técnicos propuestos: payments PENDING/SUCCEEDED/FAILED/EXPIRED;
eventos RECEIVED/PROCESSED/FAILED/IGNORED; refunds REQUESTED/PENDING/SUCCEEDED/FAILED.
Moneda inicial MXN. Stripe no tiene cajero ni sesión. Máximo un pago exitoso
por orden requiere exclusión transaccional, no solo relaciones. Payment_events
acepta FK NULL para evento válido todavía no asociado. No guardar PAN/CVV.

Ventas derivan método/cajero/sesión mediante payments. Cobro tardío excepcional
de orden definitivamente expirada se registra y reembolsa, sin generar venta
de preparación. Reembolso no borra el cobro. Referencia Stripe permite rastreo.

Solo una cash_session abierta global; garantizar exclusión en implementación.
Campos de cierre NULL hasta cerrar. Fondo 50000 + cobros 200000 = 250000;
contado 249000 da diferencia -1000 (este campo admite negativos).

Efectivo: cash_received_cents >= amount_cents y change_cents =
cash_received_cents − amount_cents. Ambos NULL para Stripe. Solo responsable
cobra/cierra; administrador puede cierre excepcional con actor/motivo registrados.
Cerrar y cobrar se excluyen transaccionalmente. Pago respeta snapshots de orden.
